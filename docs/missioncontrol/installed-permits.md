# Installed MissionControl permits

This engineering candidate binds an owner-approved MissionControl Mission, Plan and WorkOrder revision to the existing canonical MyEve AlphaTasks Work. It adds no accounting ledger, Factory execution endpoint or execution budget. The installed runtime is not qualified for activation.

An operator-provisioned `mc-owner-enrollment/v1` document pins the MyEve owner, canonical MissionControl authentication subject, installation, connection, origins, FactoryVersion, execution contract, capability baseline and Ed25519 permit keys. Request handlers cannot create or replace enrollment. A signed execution permit lives at most five minutes; a separate signed admission receipt lives at most ten seconds and binds the fresh MyEve and Relay capability decisions. MyEve rechecks canonical policy, agent revision, receiver incarnation and enrollment, policy identity, Work generation and all expiries before retaining admission. PostgreSQL repeats the currentness check before local authority admission and dispatch. Shared reservation remains in the existing accounting path.

Retained permit, receipt, Work binding, control and original Factory readback records are immutable and owner-scoped. Signed control push and reconciliation pull commit their receiving fence before acknowledgment. A fence does not establish remote cleanup or release an UNKNOWN reservation. Revoke uses the existing authenticated stop path and acknowledgment remains `PENDING_BACKEND` until canonical backend evidence establishes cleanup. A lost callback is recoverable through the retained control outbox.

The owner-only `enterprise.prepare_execution` tool prepares a MissionControl approval request for the exact canonical Work and server-enrolled limits. It cannot approve the request or reserve execution. Installed mode fails before shared reservation when enrollment is missing. Other installations retain their existing execution behavior.

The existing Factory start action reads the approved permit, authenticates a fresh MissionControl capability challenge, obtains canonical MyEve and Relay policy evidence, and retains MissionControl's signed admission receipt before the existing controller reserves or dispatches. Returning an already consumed or terminal request does not mint another permit. Relay's authenticated preparation and lease endpoints preserve its current Passport, resource ownership, policy, approval and budget checks. A lease reference is not a consumed Relay execution call.

`MYEVE_MISSIONCONTROL_RELAY_LEASE_JSON` selects an already enrolled Relay account, agent, runtime, workload, task, audience, exact capability/resource/parameters and verification key, bound to the same MyEve owner, installation, connection and enrollment revision. Separate server-held runtime/workload credentials authenticate that selection. It does not provision any authority. An operator must qualify the selected capability and trusted preparation resolver; no synthetic fixture capability is a deployment default. Fresh source evidence changes the exact Relay action digest. If Relay requires an owner approval or a metered reservation, its existing explicit procedure must supply a matching current record; the MyEve tool does not approve or invent a reservation.

The canonical operator-held MyEve enrollment must additionally pin `relayLeaseEnrollmentSha256`, the SHA-256 of the parsed Relay enrollment's canonical JSON (`relayLeaseEnrollmentDigest`). It includes the verification key and every target selection, approval and budget reference. An environment edit cannot replace that trust root; an operator must advance the immutable enrollment revision and qualify the new selection. Older enrollment evidence remains readable but cannot start installed Relay admission without the pin. This is a server enrollment trust root, not a claim that MissionControl signed this metadata. Credentials stay outside the document. The beta denies `LIMIT` and all nonempty obligations because it does not implement those semantics; a matching unexpired explicit approval still passes through Relay's canonical issuance checks.

The Result endpoint accepts only the dedicated, short-lived connection HMAC request. It refreshes the existing Factory request with the canonical signed challenge verifier; this operation cannot issue, claim, replay, stop or settle execution. It returns original signed Factory evidence, retained Result and immutable Proof with the same Mission and Work identity. Stale, nonquiescent or UNKNOWN Factory attestation remains pending, and a settled response cannot outlive its attestation. Optional observation-storage failure does not overwrite canonical authenticated execution truth. MissionControl independently verifies the evidence and must preserve PARTIAL and UNKNOWN outcomes.

## Migration and rollback

`0094_missioncontrol_permit_bindings.sql` and `0095_missioncontrol_control_acknowledgments.sql` are additive and install no enrollment, key, grant or spending authority. Existing installations retain their previous required schema until this mode is enabled. Installing the migrations on an existing database still requires the normal explicit migration authorization and a reviewed role-grant package. The canonical Work runtime must receive EXECUTE on `missioncontrol_assert_dispatch(text,uuid,integer,integer,boolean,text)` as part of that package; the installed application also needs narrowly scoped SELECT/INSERT and the documented enrollment/snapshot functions. Do not grant enrollment or policy-evidence mutations to the application role.

Control records retain an acknowledgment obligation beyond execution-permit expiry and terminal cleanup. Only an exact validated MissionControl response records delivery. Pending cleanup remains eligible for reconciliation; a failed read or acknowledgment does not starve subsequent controls. The append-only delivery receipt changes neither the fence nor accounting.

`0097_missioncontrol_control_attempts.sql` adds owner-scoped scheduling observations. Polling selects at most 100 permits by least recent attempt, with unseen permits first, and records each attempt before network I/O. A restarted worker therefore moves past permanent failures without discarding UNKNOWN controls. A full page is reported for backlog monitoring; bounded error codes distinguish invalid responses and binding failures from transport unavailability without exposing diagnostics. The application needs SELECT/INSERT/UPDATE on this observation table only; those rows convey no authority or successful delivery. Withhold table ownership, TRUNCATE and enrollment writes from all application roles.

Admission denied before canonical reservation can require a fresh policy pair on a later owner retry. This may create another unconsumed Relay lease reference. There is no automatic admission retry or paid execution from that reference; retained accounting and dispatch idempotency remain canonical. Installed qualification must verify the existing request rate limits and keep this churn visible.

Rollback disables new admissions, reconciles retained authority through the original path, and retains the additive schema and all evidence. Never delete an enrollment or undo an accounting reservation to roll back application code. A restored database cannot be activated without an independently retained recovery witness and requalification.

## Remaining qualification

The composed authenticated live-service journey, an independently retained hosted recovery witness, actual owner/Relay bindings, custody-derived FactoryVersions, the same-Mission MyApps package and hosted checks remain required. Local synthetic PostgreSQL and protocol tests are engineering evidence only. The existing hosted capability guard remains in force; this change does not turn it off.
