# Composed admission qualification

This harness uses the selected actual MissionControl Convex functions, Relay route handlers and PostgreSQL transactions, and MyEve admission/controller code. It creates isolated local fixture databases and fresh synthetic identities/keys. Relay runs in a separate process with its own canonical database. Its signed policy outbox reaches an actual Convex receiver transaction through a local fixture HTTP adapter; the adapter signs the exact acknowledgment with the enrolled fixture receiver key and returns only after the transaction commits.

MyEve's pinned HTTPS issuer requests are explicitly routed to these loopback services. This is a transport fixture, not DNS/TLS or installed authentication qualification. MissionControl's existing test admin-auth helper represents synthetic Clerk subjects; it is not an actual Clerk login. The unchanged external-alpha policy guard is supplied synthetic test configuration; the hosted capability guard is not changed or bypassed. Factory is the existing `FakeFactory`: it validates exact signed authority and provides synthetic authenticated readback, but executes no model, VM, producer or verifier. A Relay lease reference remains unconsumed; it is not evidence of a native Relay resource call.

The standard scenario covers exact-owner preparation/approval, real cross-system positive admission, duplicate delivery, disable preserving existing Work, signed revoke/acknowledgment, and Convex restart/PostgreSQL reconnection. `COMPOSED_UNKNOWN=1` covers retained ambiguous accounting, truthful pending cleanup and late signed fixture settlement being unable to clear immutable UNKNOWN exposure. Administrative accounting reconciliation remains NOT_RUN. Neither scenario qualifies an installed platform owner, the two actual testers, MyApps installation, a browser journey, protected custody or production readiness.

Run from this checkout using its locked dependencies, with explicit `COMPOSED_MC_ROOT`, `COMPOSED_RELAY_ROOT`, `COMPOSED_REPORT`, `MC_COMPATIBILITY_CONVEX_BINARY`, an unused `MC_COMPATIBILITY_PORT`, and the integration owner's disposable loopback `MYEVE_EXTERNAL_ALPHA_TEST_DATABASE`. `node --import tsx scripts/composed-admission/journey.mts` runs the standard scenario. The harness records selected source SHAs and removes only its own resources. No source or credentials in the selected component roots are modified.

MyEve's optional `relayLeaseEnrollmentSha256` is its server-only operator metadata. MissionControl retains the strict existing enrollment schema at the same revision. Never copy the extended MyEve enrollment JSON wholesale into MissionControl.

Tracked runtime source changes abort before fixtures start. Reports include exact source HEADs, source cleanliness, and harness file digests. Every owned cleanup is attempted; unconfirmed cleanup turns the report into FAIL even when functional checks passed. Relay cleanup requires both its database-cleanup acknowledgment and bounded child completion. `node --test scripts/composed-admission/cleanup.test.mjs` injects teardown failure and checks continued cleanup.
